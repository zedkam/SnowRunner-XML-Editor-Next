# SnowRunner XML Editor Next — состояние проекта

Дата диагностики: 2026-08-02

Этот файл описывает состояние локальной копии и проверенной установки игры. В папке проекта нет `.git` и полного набора `node_modules`; актуальный `initial.pak` найден на диске D и проверен в режиме чтения.

## Краткий вывод

Локальная копия подготовлена как первая тестовая версия продолжения проекта:
`2.0.0-beta.1`. Целевой публичный репозиторий: `zedkam/SnowRunner-XML-Editor-Next`.

Проект представляет собой рабочий Electron/Vue/TypeScript-редактор XML с хорошей базовой моделью разрешения файлов: модификация имеет приоритет над DLC, DLC — над базовой игрой. Главный технический долг связан не с самим XML-доменом, а с тем, что состав игрового контента зафиксирован в артефактах сборки и в сгенерированном статическом каталоге.

Для продолжения развития нужен переход от «поддержать DLC номером» к «проиндексировать фактическое содержимое установленной игры». При этом текущий редактор, bridge и UI можно мигрировать постепенно.

Официально уже выпущены Season 17: Repair & Rescue и Season 18: Patch & Power. Season 17 добавляет Zurdania, Jangsu RX600, Voron G-5352 и новые add-ons/trailers; Season 18 добавляет Chiapas, Mercer R230, HIB Billert M816 и Gooseneck Semi-Trailer with Parts.

Состав XML в актуальном архиве подтверждён: `dlc_15_5`, `dlc_16`, `dlc_16_5`, `dlc_17`, `dlc_17_5`, `dlc_18`. Extraction и generated defaults исправлены. Из 411 XML-файлов 402 проходят строгий XML-парсер; 9 отмечены как известные duplicate-attribute quirks retail-архива, неожиданных ошибок — 0. Полный UI round-trip остаётся отдельным smoke-тестом.

## Приоритетные риски

1. Будущие пути `_dlc` всё ещё не добавляются автоматически в статический optimized list.
2. Defaults и reset опираются на огромный вручную/генераторно собранный TypeScript-файл вместо данных конкретной установки.
3. XML пересериализуется через Cheerio и форматтер; без snapshot-тестов легко потерять порядок, неизвестные атрибуты или особые узлы.
4. Архивирование через WinRAR зависит от встроенного бинарного набора и статических list-файлов.
5. Bridge между main и renderer типизирован частично и широко использует `any`; ошибка контракта проявится только во время выполнения.
6. Нет отдельного понятия «версия игрового контента», поэтому результаты для разных патчей и DLC нельзя надёжно сравнивать.

## Принятые архитектурные решения

- Источником истины для доступности объекта является фактический XML/архив установленной игры, а не список DLC в исходниках.
- Номер DLC используется как метка происхождения, но не как ветка бизнес-логики.
- Неизвестные XML-узлы и атрибуты должны сохраняться; UI может их показывать как raw/advanced, но не должен молча удалять.
- `defaults` остаётся временным fallback до миграции, после чего его роль смещается к snapshot-базе и миграциям.
- Сохранение делается транзакционно: backup → temporary archive update → verify → replace.
