# Ручная агентная оркестрация SnowrunnerXML

Статус: manual orchestration v2. Каноническая ветка реализации — `codex/agent-orchestration-v2`.

## Задача архитектуры

Режим решает три практические проблемы длительной работы:

1. цель, ограничения и принятые решения переживают compaction, паузу и новое устройство;
2. специализированный исполнитель получает только нужный ему пакет, а не всю историю чата;
3. дорогая модель используется только для соответствующей фазы, а локальные Git-проверки и хранение состояния не требуют модели.

Режим ручной. Он включается через `$orkestr` или прямую просьбу применить оркестрацию сейчас. Сложность задачи, обсуждение режима и упоминание названия сами его не включают.

## Как решение встроено в существующий проект

Корень `SnowrunnerXML` не является Git-репозиторием. Единственный Git carrier с `origin` — `SnowRunner-XML-Editor-Desktop-main`. При этом действующий корневой `AGENTS.md` маршрутизирует два контура:

- XML и код редактора — `SnowRunner-XML-Editor-Desktop-main`;
- модели, Blender-сцены и моды — `SnowRunner-Modding`.

Оркестрация не повторяет и не заменяет этот маршрут. Она добавляет поверх него только execution layer:

```text
запрос пользователя
        ↓
корневой AGENTS.md → существующий контур editor | modding
        ↓
$orkestr → lifecycle + компактный task context
        ↓
.codex/agents → Astra | Terra | Sol | Luna
        ↓
проверка главным агентом → checkpoint → origin
```

Канонические файлы хранятся в Git carrier. `tools/orchestration/install-workspace-adapter.ps1` копирует только управляемые файлы в родительские `.codex/` и `.agents/skills/`, поэтому режим обнаруживается и при запуске Codex из корня всего рабочего пространства. Существующий `.codex/blender-mcp` сохраняется как unmanaged tree.

## Слои

| Слой | Source of truth | Назначение |
|---|---|---|
| Доменный маршрут | `../AGENTS.md` и проектные документы | Выбор editor/modding и их ограничения |
| Project config | `.codex/config.toml` | Включение custom agents и предел параллелизма |
| Роли | `.codex/agents/*.toml` | Точная модель, reasoning effort, sandbox и узкая ответственность |
| Навык | `instructions/agent-skills/orkestr/` | Активация, orchestration protocol и границы |
| Codex adapter | `.agents/skills/orkestr/` | Обнаруживаемая копия канонического навыка |
| Runtime | `.codex/orchestration/bin/task_state.py` | Детерминированный lifecycle состояния без AI |
| State | `codex/task-state/<task-id>` | Отдельная metadata-only orphan-ветка каждой задачи |

`tools/orchestration/sync_skill.py` синхронизирует только канонический навык в adapter. Проверка требует побайтного совпадения двух пакетов.

## Маршрутизация моделей

| Фаза | Custom agent | Модель | Причина |
|---|---|---|---|
| Архитектура и проектирование | `snowrunner_architect` | `gpt-6-astra` | Решения с последствиями и неоднозначные интерфейсы |
| XML, TypeScript, JavaScript, Python, PowerShell и файлы | `snowrunner_xml_worker` | `gpt-5.6-terra` | Реализация и проверка проектных артефактов |
| Анализ и диагностика | `snowrunner_analyst` | `gpt-5.6-sol` | Причинный разбор и evidence |
| Сводки и handoff | `snowrunner_summarizer` | `gpt-5.6-luna` | Быстрое сжатие проверенного материала |

Смешанная задача разбивается на фазы. Конфигурация не меняет модель главного thread молча: если текущая модель не соответствует фазе, оркестратор вызывает custom agent. Главный агент принимает результат и остаётся владельцем общей цели.

## Контекстный протокол

Для задачи хранятся три файла:

- `context.md` — до 12 000 символов; первый файл при продолжении;
- `state.json` — полный структурированный checkpoint;
- `events.jsonl` — компактная история, читаемая только для диагностики.

Исполнителю передаётся пакет до 6000 символов: цель подзадачи, разрешённые пути, необходимые ссылки, ограничения, критерии приёмки и формат evidence. Полная история родителя не передаётся; рекомендуемый режим — `fork_turns = "none"`. В корневой контекст возвращаются только проверенный вывод, изменённые пути, результаты проверок и нерешённые блокировки.

Checkpoint обязателен после решения, принятого результата, завершённой фазы, пользовательской коррекции и перед паузой/compaction/архивированием. Luna может сжать материал, но не имеет права добавлять решения.

## Жизненный цикл состояния

Каждый cache задачи является отдельным маленьким Git-репозиторием с тем же `origin`. Первая фиксация создаёт orphan-ветку `codex/task-state/<task-id>`, не имеющую общей истории с `main`. Ветка содержит только `.codex/task-state/<task-id>/` и отправляется в `origin` после каждого checkpoint.

Это даёт два свойства:

- ветку состояния нельзя случайно включить обычным fast-forward или штатным merge в продуктовую ветку;
- восстановление не требует исходной истории чата: достаточно клонировать точную ветку и прочитать `context.md`.

Архивирование меняет статус на `archived`, но сохраняет remote-ветку и cache. Окончательное удаление требует точного совпадения `--task-id` и `--confirm-task-id`, проверяет remote и чистоту cache, затем удаляет только эту ветку и эту папку.

Codex UI сейчас не предоставляет проекту автоматическое событие удаления/очистки архива. Поэтому очистка выполняется вручную; скрытой имитации hook нет.

## Принятие уже выполненной работы

При включении режима в начатой задаче runtime может записать:

- относительный рабочий путь;
- краткое подтверждённое описание принятого результата;
- Git root, branch, HEAD, `status --short` и `diff --stat`, если путь находится в Git;
- ограничения и открытые вопросы.

Найденные изменения не объявляются правильными автоматически и не коммитятся в state-ветку. Главный агент сначала проверяет их происхождение и фактическое состояние.

## Восстановление файлов и ограничения

State-ветка восстанавливает контекст, решения, evidence и относительные пути. Она не является резервной копией больших `.blend`, FBX, meshbin, DDS, native-файлов или оригинальных игровых ресурсов из `00_source/`. Такие файлы должны находиться в разрешённом отдельном хранилище; их автоматическая отправка в Git противоречила бы существующим правилам прав и релиза.

Изменения редактора и скриптов хранятся в обычной рабочей/feature-ветке. State-ветка на неё ссылается по branch/commit, но никогда с ней не сливается.

## Защищённые границы

- Корневой `AGENTS.md` только читается; установщик сверяет его SHA-256 до и после операции.
- `.codex/blender-mcp` не входит в managed files; установщик сверяет дерево до и после.
- `main` не переключается и не изменяется установщиком.
- Чужой dirty worktree не очищается, не сбрасывается и не переносится.
- Установщик останавливается при конфликте управляемого файла. `-Force` затрагивает только точные managed paths и предварительно сохраняет их копии.

## Проверки готовности

Перед фиксацией должны пройти:

```powershell
python tools/orchestration/sync_skill.py --check
python tools/orchestration/validate_orchestration.py
python tools/orchestration/test_task_state.py
powershell -NoProfile -ExecutionPolicy Bypass -File tools/orchestration/install-workspace-adapter.ps1 -Mode Check
git diff --check
```

Дополнительно canonical и adapter проверяются bundled `quick_validate.py` навыка `skill-creator`.
