# Оркестр SnowrunnerXML

Ручной режим сохраняет цель и решения вне истории чата, выдаёт исполнителям только минимальный контекст и закрепляет модель за типом работы. Пользовательский запрос и действующие инструкции проекта имеют приоритет над этим навыком.

## Активация

Включай режим только при явном намерении пользователя применить его сейчас:

- точный вызов `$orkestr`;
- прямая просьба включить, запустить, использовать или продолжить оркестрацию;
- та же просьба в свободной русской речи, с очевидной опечаткой, неверной раскладкой или шумом голосовой расшифровки.

Не включай режим из-за сложности задачи. Упоминание названия, обсуждение принципов, пример команды, вопрос о возможностях, отрицание или просьба ничего не запускать не являются активацией. При сомнении продолжай обычный режим и не задавай отдельный вопрос только ради включения. Для пограничных формулировок читай [правила активации](references/activation.md).

## Существующий маршрут проекта

Сначала применяй корневой `AGENTS.md` рабочего пространства и инструкции выбранного контура. Оркестрация не создаёт новый доменный маршрутизатор:

- XML-редактор остаётся в `SnowRunner-XML-Editor-Desktop-main/`;
- модели, Blender и моды остаются в `SnowRunner-Modding/`;
- ограничения источников, прав, `object.json`, фаз объекта и обязательных проверок сохраняются.

## Начало или продолжение

Определи один из трёх случаев без лишнего вопроса:

1. Новая задача: создай устойчивый `task-id` и новое состояние.
2. Режим включён в уже начатой задаче: сначала прими только подтверждённо выполненную работу, текущие ограничения и фактический Git/file state; затем создай состояние с отметкой `accepted_work`.
3. Возобновление: получи точный `task-id`, восстанови ветку из `origin` и сначала прочитай только `context.md`. Открывай `state.json` для деталей; `events.jsonl` — только для расследования истории.

Если идентификатор сохранённой задачи нельзя однозначно определить, это влияет на объект восстановления — задай один короткий вопрос. В остальных случаях исследуй репозиторий и выбирай безопасные технические детали самостоятельно.

Команды жизненного цикла и формат состояния описаны в [протоколе состояния](references/state-protocol.md).

## Работа оркестратора

Главный агент остаётся единственным интегратором: держит цель и полномочия, принимает или отклоняет результаты, разрешает противоречия и фиксирует checkpoints.

1. Составь короткий граф фаз и выдели только независимые, ограниченные подзадачи.
2. Не создавай исполнителя для операции, которую быстрее и дешевле выполнить локальной командой без рассуждения.
3. Одновременно запускай не более трёх исполнителей. Параллельные записи допустимы только в непересекающихся worktree или путях.
4. Предпочитай исполнителя без истории родителя (`fork_turns = "none"`) и передавай ему пакет до 6000 символов: цель подзадачи, разрешённые пути, обязательные ссылки, ограничения, критерии приёмки и нужный формат evidence.
5. Не копируй в корневой контекст полные логи и рассуждения исполнителя. Прими компактный результат только после проверки файлов и evidence.
6. Последовательные или небольшие задачи выполняй одним агентом. Оркестрация нужна для изоляции контекста, а не для максимального числа агентов.

Обычная задача вне этого режима может точечно использовать дополнительного исполнителя по прямой просьбе или действующим инструкциям, но не создаёт persistent state автоматически.

## Обязательная маршрутизация моделей

- Архитектура, проектирование, интерфейсы и продуктовые развилки — `snowrunner_architect` на `gpt-6-astra`.
- Изменение и проверка XML, TypeScript, JavaScript, Python, PowerShell и других проектных файлов — `snowrunner_xml_worker` на `gpt-5.6-terra`.
- Анализ, диагностика, исследование репозитория и причин — `snowrunner_analyst` на `gpt-5.6-sol`.
- Сводки, классификация, компактные checkpoints и handoff — `snowrunner_summarizer` на `gpt-5.6-luna`.

Смешанную задачу разделяй по фазам. Если текущая модель уже совпадает с нужной ролью, работа может остаться у главного агента. Иначе передай фазу исполнителю с точной моделью. Не подменяй обязательную модель похожей; при недоступности нужной модели сохрани checkpoint и честно сообщи блокировку.

## Сохранение контекста

Состояние задачи — source of truth для продолжения, а не история чата. Обновляй его:

- после принятого архитектурного решения или пользовательской коррекции;
- после принятия результата исполнителя;
- после завершения фазы или значимой проверки;
- перед паузой, compaction, архивированием или передачей на другое устройство.

`context.md` должен оставаться не длиннее 12000 символов и содержать только цель, ограничения, принятые решения, выполненное, текущее состояние, evidence, открытые вопросы и следующие действия. Luna может подготовить сжатие, но главный агент проверяет его и не разрешает добавлять новые решения.

Никогда не записывай в state, context, event log или Git remote пароли, токены, ключи, cookies, session data и другие секреты. Вместо значения сохраняй только безопасное описание того, какого локального доступа не хватает.

## Ветки и завершение

Каждая задача хранит metadata-only состояние в самостоятельной orphan-ветке `codex/task-state/<task-id>`. После каждого checkpoint отправляй её в `origin`. Никогда не сливай такую ветку в `main`, `dev` или рабочую feature-ветку.

Архивирование переводит состояние в `archived`, фиксирует последний checkpoint и сохраняет ветку и локальный cache. Окончательное удаление выполняй только отдельной ручной командой с подтверждённым точным `task-id`; она удаляет ровно соответствующую remote-ветку и cache. События удаления/очистки архива Codex UI автоматически не перехватываются.

Перед выходом из режима сохрани checkpoint и сообщи пользователю `task-id`, статус, ветку состояния и следующий шаг.
